# HMCTS Dev Test Backend

A REST API that lets HMCTS caseworkers create and manage their tasks. Built with **Python**, **FastAPI**, **SQLAlchemy** and **SQLite**.

The frontend for this API lives in [hmcts-dev-test-frontend](https://github.com/Mmeso1/hmcts-dev-test-frontend).

## Features

- Create, retrieve, list, update the status of, and delete tasks
- Data stored in a SQLite database (`tasks.db`, created automatically)
- Request validation with clear error messages
- Consistent JSON error responses (`404` for missing tasks, `422` for invalid input)
- Interactive API documentation (Swagger UI)
- Unit and API tests with pytest

## Requirements

- Python 3.11 or later

## Getting started

```bash
# 1. Create and activate a virtual environment
python3 -m venv .venv
source .venv/bin/activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Start the API on port 4000
uvicorn app.main:app --reload --port 4000
```

The API is now running at http://localhost:4000. Port 4000 is the port the frontend expects.

## API documentation

With the API running, open:

- **Swagger UI:** http://localhost:4000/docs (try every endpoint from the browser)
- **ReDoc:** http://localhost:4000/redoc
- **OpenAPI spec:** http://localhost:4000/openapi.json

### Endpoints

| Method   | Endpoint              | Description                 | Success | Errors     |
|----------|-----------------------|-----------------------------|---------|------------|
| `GET`    | `/`                   | Health check                | `200`   |            |
| `POST`   | `/tasks`              | Create a task               | `201`   | `422`      |
| `GET`    | `/tasks`              | Retrieve all tasks          | `200`   |            |
| `GET`    | `/tasks/{id}`         | Retrieve a task by ID       | `200`   | `404`      |
| `PATCH`  | `/tasks/{id}/status`  | Update the status of a task | `200`   | `404`, `422` |
| `DELETE` | `/tasks/{id}`         | Delete a task               | `204`   | `404`      |

### Task fields

| Field         | Type                                  | Required | Notes                                |
|---------------|---------------------------------------|----------|--------------------------------------|
| `id`          | integer                               | –        | Generated by the database            |
| `title`       | string (1–255 chars)                  | Yes      | Must not be blank                    |
| `description` | string (max 2000 chars)               | No       |                                      |
| `status`      | `TODO` \| `IN_PROGRESS` \| `DONE`     | No       | Defaults to `TODO`                   |
| `due_date`    | ISO 8601 date-time                    | Yes      | e.g. `2026-12-01T09:00:00`           |
| `created_at`  | ISO 8601 date-time                    | –        | Set automatically                    |

### Examples

Create a task:

```bash
curl -X POST http://localhost:4000/tasks \
  -H "Content-Type: application/json" \
  -d '{"title": "Review case file 1234", "description": "Check the evidence bundle", "due_date": "2026-12-01T09:00:00"}'
```

```json
{
  "id": 1,
  "title": "Review case file 1234",
  "description": "Check the evidence bundle",
  "status": "TODO",
  "due_date": "2026-12-01T09:00:00",
  "created_at": "2026-11-05T10:15:00"
}
```

Update its status:

```bash
curl -X PATCH http://localhost:4000/tasks/1/status \
  -H "Content-Type: application/json" \
  -d '{"status": "DONE"}'
```

Error response for a missing task:

```json
{ "detail": "Task with id 99 was not found" }
```

## Running the tests

```bash
pytest
```

- `tests/test_task_service.py`: unit tests for the business logic, using an in-memory repository instead of a database
- `tests/test_tasks_api.py`: tests for every endpoint, including validation and error cases, against an in-memory SQLite database

## Project structure

```
app/
├── main.py                       # Creates the FastAPI app and registers routes and error handlers
├── config.py                     # Settings (e.g. DATABASE_URL)
├── database.py                   # Database engine and session handling
├── exceptions.py                 # AppError and TaskNotFoundError
├── models/
│   ├── base.py                   # Declarative base class shared by all models
│   └── task.py                   # Task database model and TaskStatus enum
├── schemas/task.py               # Request/response models with validation
├── repositories/
│   ├── base.py                   # Abstract BaseRepository interface
│   └── task_repository.py        # SQLAlchemy implementation
├── services/task_service.py      # Business logic
└── api/tasks.py                  # HTTP endpoints
tests/
```

## Design

The code is split into layers, each with a single responsibility:

```
Router (api/tasks.py)  →  TaskService  →  TaskRepository  →  SQLite
```

- **Router**: handles HTTP only (paths, status codes, request/response models).
- **TaskService**: business logic such as "a task must exist before it can be updated".
- **TaskRepository**: database access only.

`TaskService` depends on the abstract `BaseRepository` rather than a concrete class, and its repository is passed in through the constructor. This lets the unit tests swap in an `InMemoryTaskRepository` without changing the service. Errors are modelled as a small class hierarchy (`AppError` → `TaskNotFoundError`), and one exception handler turns them into consistent JSON responses.
