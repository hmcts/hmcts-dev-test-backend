# HMCTS Dev Test Backend

Spring Boot service for the HMCTS case management system, connected to PostgreSQL and shipped as a
container. This repo holds the app configuration, the CI/CD pipeline, and the Terraform definition of
its Azure infrastructure.

## Running it locally

You need Docker with the Compose plugin. You don't need a JDK or a local PostgreSQL.

```bash
cp .env.example .env
docker compose up --build --wait
```

`--wait` blocks until both containers report healthy. The app's healthcheck hits
`/health/readiness`, and the readiness group contains only the `db` indicator. so if `--wait`
returns cleanly, the service has connected to the database. The first build takes a few minutes while
Gradle resolves dependencies.

```bash
curl http://localhost:4000/                  # Welcome to test-backend
curl http://localhost:4000/get-example-case  # sample case JSON
curl http://localhost:4000/health            # {"status":"UP","components":{"db":{...}}}
curl http://localhost:4000/health/readiness  # UP only when the DB is reachable
```

To confirm the health check isn't just always green:

```bash
docker compose stop db
curl -i http://localhost:4000/health/readiness   # 503, DOWN
docker compose start db                          # back within a probe interval
```

Other bits: `docker compose logs -f app`, `docker compose ps` for health status,
`docker compose down --volumes` to wipe the database. Set `APP_HOST_PORT` / `DB_HOST_PORT` in `.env`
if 4000 or 5432 are taken.

If you'd rather run from Gradle, the app needs a database first:

```bash
docker run -d --name pg -e POSTGRES_PASSWORD=localdev -e POSTGRES_USER=devtest \
  -e POSTGRES_DB=devtest -p 5432:5432 postgres:16-alpine

DB_HOST=localhost DB_PORT=5432 DB_NAME=devtest \
DB_USER_NAME=devtest DB_PASSWORD=localdev ./gradlew bootRun
```

### Credentials

Nothing is hardcoded. Compose reads every credential from the environment using `${VAR:?message}`,
so it aborts with a named error rather than starting with a blank password. `.env` is gitignored.
I removed it from version control, since it's now the file holding a password and `.env.example` is
the committed template with throwaway placeholders. In Azure the password is generated by Terraform
and stored in Key Vault.

## Part 1: what I changed

`build.gradle` gets `spring-boot-starter-jdbc` and `runtimeOnly org.postgresql:postgresql`. I used
the JDBC starter rather than `data-jpa` because nothing persists entities yet, the JDBC starter is
all `DataSourceHealthIndicator` needs, and JPA would add Hibernate and entity scanning for no current
benefit. Both versions come from the Spring Boot BOM rather than being pinned by hand. The driver is
`runtimeOnly` because no application code compiles against it.

In `application.yaml` I uncommented the datasource block, added `health` to the exposure list, and
enabled the `db` readiness group. `poolName` needed a real value in place of the `{to-be-defined}`
placeholder. I also made `server.port` read `${SERVER_PORT:4000}` so it can be overridden without a
rebuild.

That gives two health endpoints doing different jobs, which matters for the probes:

- `/health` — aggregate. Used for **liveness**. Restarting doesn't fix a database outage, so a DB
  blip shouldn't kill the container.
- `/health/readiness` — `db` only. Used for **readiness**, so a replica that can't reach PostgreSQL
  drops out of the load balancer but stays up to recover.

Pointing liveness at the db indicator is an easy way to turn a brief database hiccup into a restart
loop, so I kept them separate.

The `Dockerfile` is JDK-alpine to build, JRE-alpine to run, so the final image has no compiler,
Gradle, or source in it. Build files are copied before source so a code change doesn't re-resolve
dependencies. It runs `assemble` rather than `build` — tests and Checkstyle are pipeline gates, and a
failing test should be a red CI job rather than something buried in docker build output. The app runs
as `appuser` (uid 1001), and the `HEALTHCHECK` uses the `wget` already in busybox so there's no extra
package to patch. `MaxRAMPercentage` sizes the heap against the container limit rather than the
host's memory.

## Part 2: the pipeline

[.github/workflows/ci.yml](.github/workflows/ci.yml). Runs on PRs to `master`, pushes to `master` and
`feature/**`, `v*.*.*` tags, and manual dispatch.

- **Build & test** — `./gradlew build` on JDK 21, which also runs the integration suite via
  `check.dependsOn integration`. Reports uploaded even on failure.
- **Static analysis** — Checkstyle across all five source sets. The `uk.gov.hmcts.java` plugin
  already wires it into `build`; I broke it out so a style failure is obvious at a glance instead of
  hidden inside the test job, and so it runs in parallel.
- **Terraform checks** — `fmt -check -recursive`, `init -backend=false`, `validate`. No credentials
  needed.
- **Build & scan image** — builds, scans with Trivy, pushes to GHCR.
- **Compose smoke test** — brings up the real stack and asserts `/health/readiness` is UP and
  `/health` has a `db` component.
- **CI passed** — aggregates the rest into one status check, which is the one to require in branch
  protection.
- **Deploy** — `terraform init/plan/apply` over OIDC, then polls the deployed health endpoint.

### Branch behaviour

| | Feature branch / PR | `master` | `v*.*.*` tag |
| --- | --- | --- | --- |
| Build, test, Checkstyle, Terraform checks | yes | yes | yes |
| Image build + Trivy scan | yes | yes | yes |
| Compose smoke test | yes | yes | yes |
| Push to GHCR | **no** | `sha-…`, `edge` | `sha-…`, semver, `latest` |
| Deploy | no | `test` | `prod` |
| Cancelled by a newer push | yes | no | no |

Feature branches get the same verification but publish nothing, a fork PR shouldn't be able to push
to our registry, and the scan is still worth running even when the image is thrown away. `master` and
tags aren't cancelled mid-run because they may be part-way through a push.

### Image tagging

Every build gets `sha-<short-sha>`. On top of that: `<branch>-<run-number>` on a feature branch,
`edge` on `master`, and `X.Y.Z` / `X.Y` / `latest` on a version tag.

The SHA tag is the only genuinely immutable one, so it's the only thing a deploy references. the
`container_image` variable has a validation rule rejecting a reference with no explicit tag or digest.
The others are conveniences for humans: `edge` for a shared dev environment, semver for anyone who
wants a stable line. If production pointed at a moving tag, "what's actually running?" would have no
reliable answer and a rollback would be guesswork. Semver comes from pushing a git tag, so cutting a
release stays a deliberate act rather than a side effect of merging.

### Scanning

Trivy runs three times against the locally-loaded image before anything is pushed: CRITICAL with
`exit-code: 1` (blocks), HIGH with `exit-code: 0` (warns), and a CRITICAL/HIGH/MEDIUM SARIF upload so
findings are tracked in the Security tab rather than just sitting in a log.

The gating scans use `ignore-unfixed`. Blocking a release on a base-image CVE with no patch available
gives the team nothing to act on, which is how people learn to route around the gate; those findings
still show up in the SARIF. The image is built with `load: true, push: false` and only pushed after
the scan passes, so a vulnerable image never reaches the registry even briefly.

### Running the pipeline in a fork

Everything except deploy works with no setup. The deploy job is guarded by
`vars.AZURE_DEPLOY_ENABLED == 'true'` so the pipeline stays green without Azure access. To turn it
on, set that variable plus `TFSTATE_RESOURCE_GROUP`, `TFSTATE_STORAGE_ACCOUNT`, and the
`AZURE_CLIENT_ID` / `AZURE_TENANT_ID` / `AZURE_SUBSCRIPTION_ID` secrets for an OIDC-federated app
registration.

## Part 3: Terraform

```
terraform/
├── versions.tf     providers, commented-out azurerm backend
├── variables.tf    inputs, typed and validated
├── main.tf         naming/tagging locals, resource group, VNet, subnets, private DNS
├── postgres.tf     Flexible Server, application database, server config
├── keyvault.tf     Key Vault, managed identity, RBAC, secrets
├── container_app.tf  Log Analytics, Container Apps environment and app
└── outputs.tf
```

```bash
cd terraform
terraform fmt -check -recursive
terraform init -backend=false
terraform validate
```

Both pass on Terraform 1.15.8 with azurerm 4.81.0. `plan` isn't expected to work without
credentials, since the azurerm provider authenticates during planning.

The config creates a resource group, a VNet with two subnets (one delegated to PostgreSQL, one for
Container Apps), a private DNS zone, a private-access Flexible Server with the application database,
Key Vault, a user-assigned managed identity, a Log Analytics workspace, and the Container App.
PostgreSQL has no public endpoint and is only reachable from inside the VNet. Prod gets zone-redundant
HA and geo-redundant backups; lower environments don't, because the cost isn't worth it there.

### Why Container Apps over App Service

The deployable unit is the exact image CI built and scanned, with no App Service-specific packaging in
between. Revisions give blue/green and single-command rollback without needing deployment slots. KEDA
autoscaling works on concurrent requests rather than just CPU, which suits a caseworker tool that's
busy in working hours and idle overnight. And VNet injection puts it in the same network as the
database without needing regional VNet integration.

The trade-off is weaker support for legacy Windows/.NET workloads and no portal deployment slots,
neither of which matters for a Linux Spring Boot service.

### How the password gets to the app

Terraform generates it with `random_password`, writes it straight to Key Vault, and the Container App
reads it at runtime through a Key Vault reference resolved by its managed identity. Nobody types it,
it isn't a variable, and it never appears in the repo.

I used a **user-assigned** identity rather than system-assigned deliberately: a system-assigned
identity is recreated along with the app, so replacing the app mints a new principal and you can land
a deployment that can't read its own password until the role assignment catches up.

Everything else is a plain environment variable matching the placeholders in `application.yaml` —
`DB_HOST` (the server's private FQDN), `DB_PORT`, `DB_NAME`, `DB_USER_NAME`, `SERVER_PORT`, and
`DB_OPTIONS=?sslmode=verify-full`.

### Conventions

Names are `<azure-abbreviation>-<product>-<component>-<env>`, e.g. `ca-hmcts-dev-test-backend-prod`.
Key Vault and the PG server need globally unique names, so they get a `random_string` suffix held in
state; the Key Vault prefix is truncated explicitly to stay under the 24-character limit rather than
failing at apply time. Every resource gets `local.tags`, `common_tags` plus `environment`, `product`,
`component`, and `builtFrom` (the git SHA, so a running deployment traces back to a commit).

Variables are all typed and described, with validation on `env`, `product`, `component`,
`container_image`, storage, backup retention and replica counts. The registry credentials are
`sensitive` with `null` defaults, so a public image needs none and a private one takes them from
pipeline secrets. No output exposes a secret `key_vault_name` and `db_password_secret_name` point
an operator at the vault instead.

### State

The `backend "azurerm"` block in [versions.tf](terraform/versions.tf) is commented out so
`init -backend=false` and `validate` run without credentials. CI passes the real values with
`-backend-config` at init time, which is also what lets the same code target every environment.

For real, state would live in a storage account provisioned by a separate bootstrap stack. a config
can't sensibly create the account holding its own state. That account wants blob versioning and soft
delete so a corrupted state file is recoverable, a `CanNotDelete` lock, no public blob access, and
RBAC-only auth (`use_azuread_auth = true`) with the pipeline's OIDC identity granted Storage Blob
Data Contributor, so there's no storage key anywhere. Locking comes free, the azurerm backend takes
a blob lease, and the pipeline passes `-lock-timeout=5m` so a concurrent run queues instead of
failing.

One state file per environment, keyed by path, so a mistake in `test` can't touch `prod`. State still
has to be treated as sensitive: the generated password is in it in plaintext, which is why access is
RBAC-gated and why nothing reads it back out of state.

## Assumptions and trade-offs

**Assumptions.** There's no schema and no migrations, the brief rules out Java changes, so the
database is connected but empty and nothing owns a schema yet. The `db` health indicator only runs a
validation query, so it proves connectivity without needing tables. Single region, no DR site. The
admin login doubles as the application login, which is fine for a test but is the first thing I'd
change. I took "behave differently on feature branches versus main" to mean `master` → `test` and a
tag → `prod`; the real branching strategy would come from the team. And `sslmode=verify-full` depends
on the DigiCert root Azure presents being in the JDK truststore. it is for current Temurin images,
but it's worth knowing about, with `require` as the fallback.

**Trade-offs I made on purpose.** The Dockerfile compiles from source instead of copying a CI-built
jar, which costs a second compile but means the image is reproducible from the repo alone. Alpine
bases are small and so have less to patch, at the cost of musl rather than glibc. no native
libraries here, so it doesn't bite. HIGH findings warn rather than block, per the brief; in a
long-lived repo I'd pair that with a scheduled scan of the deployed image and an SLA, so "warning"
doesn't quietly become "ignored". I also stuck with a fat jar rather than Spring Boot's layered-jar
extraction: layers would cache better, but I couldn't verify the `-Djarmode=tools extract` invocation
here (see below) and I'd rather ship something correct than something clever and untested.

**With more time**, in rough priority order:

1. Drop the admin account for the app. Enable Entra authentication on the Flexible Server and connect
   as the managed identity with a passwordless token, which removes the stored password entirely.
   Failing that, a least-privilege application role with its own Key Vault secret, keeping admin for
   break-glass.
2. Own the schema with Flyway, run as a pre-deploy step so schema changes are reviewed like code.
3. Front Door + WAF instead of the Container App's public FQDN, and a private endpoint on Key Vault.
4. Pin actions and base images by digest rather than tag, and let the existing Renovate config bump
   them.
5. Application Insights, plus alerts on readiness failures, Hikari pool saturation and 5xx rate.
6. `tflint` and `checkov` in the Terraform job, and `plan` posted as a PR comment on infra changes.
7. Bring back the OWASP dependency check (already configured with a suppression file) as a scheduled
   job with an NVD API key, too slow for the per-push path.
8. Split Terraform into network/data/compute modules once there's more than one service.
9. Wire up the `functional` and `smoke` Gradle suites, which exist but aren't run `smoke` against a
   deployed environment as a post-deploy gate.

## What I verified, and what I didn't

`terraform fmt -check -recursive` and `terraform validate` pass locally against azurerm 4.81.0 on
Terraform 1.15.8. Doing that caught a real deprecation, `enable_rbac_authorization` →
`rbac_authorization_enabled`. The workflow and Compose YAML parse, with the health, exposure and
datasource keys resolving to what I expected.

I could not run `./gradlew build` or `docker compose up`, the machine I wrote this on has no JVM and
no container runtime. The `compose-smoke` job exists to cover that gap on the first push: it builds
the image, brings the stack up, and asserts the database-backed health endpoints. If you're reviewing
this from a fresh clone, that job is the thing to look at, because it's what proves the Part 1 wiring
works rather than merely parses.
